# Голосовой ассистент для записи в поликлинику

Голосовой ассистент для государственной поликлиники, который принимает входящие звонки пациентов, записывает на приём, переносит и отменяет записи, напоминает о визитах и отвечает на типовые справочные вопросы. Работает параллельно с регистраторами, автоматизируя типовые сценарии и передавая сложные и медицинские обращения живому оператору.

> **Хакатон:** Задача № 2 «Голосовые интерфейсы»  
> **Заказчик:** государственная бюджетная поликлиника (~120 000 прикреплённых, 85 врачей, 12 регистраторов)  
> **Целевые метрики:** доля пропущенных звонков ≤ 15%, доля неявок ≤ 12%, ≥ 60% типовых звонков без оператора, ожидание на линии ≤ 30 сек, NPS ≥ 4/5

## Что умеет ассистент

### Полностью автоматизированные сценарии (C-01…C-09)

| Код  | Сценарий                              |
|------|---------------------------------------|
| C-01 | Запись к терапевту                    |
| C-02 | Запись по направлению к специалисту   |
| C-03 | Перенос существующей записи           |
| C-04 | Отмена записи                         |
| C-05 | Проверка статуса записи               |
| C-06 | Вызов врача на дом                    |
| C-07 | Справка о графике работы врача        |
| C-08 | Справка о готовности анализов         |
| C-09 | Справка о платных услугах             |

### Исходящие сценарии

| Код  | Сценарий                                   |
|------|--------------------------------------------|
| C-10 | Напоминание о визите за день до приёма     |
| C-11 | Предложение слота из листа ожидания        |

### Обязательная эскалация на оператора

| Код  | Сценарий                                                        |
|------|-----------------------------------------------------------------|
| C-14 | Красный флаг (острая боль, неотложное состояние)                |
| C-15 | Жалоба, нестандартный вопрос, просьба о медицинской консультации |

Ассистент **не ставит диагнозы, не рекомендует препараты и не оценивает симптомы**. При любом признаке красного флага разговор немедленно переводится на регистратора.

## Архитектура

Проект построен по слоистой архитектуре с чётким разделением ответственности. Зависимости направлены **сверху вниз**: Presentation → Application → Domain → Infrastructure.

```text
┌─────────────────────────────────────────────────┐
│  Presentation Layer (API)                       │
│  app/api/                                       │
│  - HTTP endpoints, WebSocket                    │
│  - валидация через Pydantic-схемы               │
│  - НЕ содержит бизнес-логики                    │
└──────────────────┬──────────────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────────────┐
│  Application Layer (Services)                   │
│  app/services/                                  │
│  - диалоговый движок, NLU, красные флаги        │
│  - оркестрация: вызывает MIS-клиент, БД, Redis  │
│  - НЕ знает про HTTP и WebSocket                │
└──────────────────┬──────────────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────────────┐
│  Domain Layer (Core)                            │
│  app/core/                                      │
│  - константы, исключения, time_utils            │
│  - правила: коды результатов, форматы дат       │
│  - НЕ зависит ни от чего                        │
└──────────────────┬──────────────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────────────┐
│  Infrastructure Layer                           │
│  app/models/, app/db.py, app/redis_client.py,   │
│  app/services/mis_client*.py, app/tasks/        │
│  - SQLAlchemy, Redis, httpx, APScheduler        │
│  - внешние адаптеры: MIS, БД, кэш               │
└─────────────────────────────────────────────────┘
```

### Ключевые архитектурные решения

1. **Гибрид LLM + FSM.** GigaChat с Function Calling извлекает интенты и слоты из свободной речи, но маршрутизацию по сценариям регламента ведёт детерминированная Python state machine (C-01…C-15). Это даёт предсказуемость, тестируемость и соответствие регламенту.
2. **MIS-клиент за Protocol.** `MISClientProtocol` с двумя реализациями (`mis_client.py` — реальный httpx, `mis_client_mock.py` — in-memory) и фабрикой `mis_factory.py`. Переключение — через `MIS_USE_MOCK` в `.env`, код не меняется.
3. **Контроль слотов на нашей стороне.** Стенд «Регистратура» не хранит расписание и не проверяет занятость — это делает `app/services/schedule.py` на основе `data/schedule.xlsx`.
4. **152-ФЗ by design.** ASR и TTS локальные, ПДн маскируются в `app/core/security.py`, аудио не уходит во внешние облака.
5. **Мок как first-class citizen.** Все тесты C-01…C-15 гоняются на моке, реальный стенд дёргается только в интеграционных и e2e.

## Быстрый старт

### Требования

- Docker 24+ и Docker Compose v2
- GNU Make
- (опционально) Python 3.11+ для локальной разработки без Docker

### Запуск

```bash
# 1. Клонировать репозиторий
git clone <url> voice_assistant_for_a_clinic
cd voice_assistant_for_a_clinic

# 2. Скопировать шаблон окружения
cp .env.example .env
# отредактировать .env — заполнить MIS_TOKEN и прочее

# 3. Поднять весь стек
make up

# 4. Проверить, что сервис жив
curl http://localhost:8000/health
```

После запуска:

- API: http://localhost:8000
- Swagger: http://localhost:8000/docs
- ReDoc: http://localhost:8000/redoc

### Остановка

```bash
make down          # остановить контейнеры
```

## Соответствие 152-ФЗ

Решение проектировалось с учётом требований к обработке персональных данных:

- **Локальный ASR и TTS.** GigaAM и Silero TTS работают в контуре заказчика — аудио не покидает инфраструктуру поликлиники. Бесплатные облачные STT (Google, Yandex, OpenAI) **не используются**.
- **Маскирование ПДн.** `app/core/security.py` маскирует ФИО, телефоны и номера полисов в логах и при передаче во внешние сервисы.
- **Обезличивание аналитики.** Речевая аналитика ведётся только по обезличенным данным или с согласия пациента.
- **Прод-LLM в контуре.** На этапе хакатона используется GigaChat API, в проде — локальная LLM (Qwen2.5 / Llama 3.1) согласно ПП № 1119 и приказу ФСТЭК № 21.
- **Соответствие уровню защищённости УЗ-1** и наличие аттестата ИСПДн — требование для прод-эксплуатации.

## Тестовый стенд «Регистратура»

На хакатоне вместо реальной МИС «Инфоклиника» используется тестовый стенд организаторов.

- **База:** `https://crm-med-mock.dbi-testing.ru/api/v1`
- **Документация:** https://crm-med-mock.dbi-testing.ru/docs
- **OpenAPI:** https://crm-med-mock.dbi-testing.ru/docs/openapi.json
- **Авторизация:** `Authorization: Bearer <токен команды>`
- **Лимит:** 10 запросов в минуту на команду

### Особенности, которые учитывает ассистент

1. Стенд **не хранит расписание** и **не проверяет занятость слотов** — контроль на нашей стороне (`schedule.py`).
2. Даты — строки `ДД.ММ.ГГГГ`, дата-время — `ДД.ММ.ГГГГ ЧЧ:ММ`, часовой пояс **GMT+4**.
3. Повторная регистрация клиента → **200**, а не 201.
4. `client_id` чужой команды → **400**, не 404.
5. `PATCH /visits` к отменённой/завершённой записи → **409**.
6. К деактивированному врачу: создание → **400**, PATCH → **409** (кроме `status=Отменена`).
7. Превышение лимита → **429** + заголовок `Retry-After`.

### Два режима работы

- `MIS_USE_MOCK=true` — in-memory мок, работает без токена (разработка и тесты).
- `MIS_USE_MOCK=false` — реальный httpx-клиент к стенду (интеграция и демо).
